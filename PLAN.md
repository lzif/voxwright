# voxwright: monorepo plan (PLAN.md)

Nov 2, 2026 · @Luki Zainur

voxwright is one AGPL-3.0 pnpm monorepo holding a TypeScript port of mcbuilder (the programmatic build engine) and a browser schematic editor, its human-in-the-loop companion; M0 scaffolds `core` and the first two codecs, and the mcbuilder port comes last so the editor is not delayed.

## Decisions

Everything in this table is settled. Where the code differs from the v1 spec and this table does not say so, the difference is listed in "Differences from the v1 spec (decided 2026-11-07)" below, each with Luki's verdict; those are settled too.

## Repository layout

One workspace under a single AGPL-3.0 `LICENSE`; each package is written as if it could be published alone, under the `@voxwright/*` npm scope.

```text
/
  packages/
    core/        Volume, NBT, block-state strings, rotation, codecs, editor core (commands, undo, tools, picking)
    render/      Renderer interface, model-to-quads, section mesher, WebGL, CPU rasterizer
    mcbuilder/   CLI for agent-built structures, ported from Python
  apps/
    web/         SvelteKit viewer, editor, converter
  fixtures/      schematics saved by real tools, shared by all tests
  vectors/       golden JSON exported from the Python mcbuilder
  PLAN.md        this plan
  LICENSE        AGPL-3.0 for everything
```

- The web app's interface uses the Ore UI Study design system (`docs/design-system.md`).
- Dependencies point one way: `apps/web` and `mcbuilder` use `render` and `core`, `render` uses `core`, and `core` imports nothing from the others and has no DOM dependency. dependency-cruiser enforces it in CI.
- Every source, script, document and workflow file carries an SPDX header.
- CI has three jobs. `repo` (Biome, dependency-cruiser) and `web` (build the site and drive it in Chrome) run on every push and pull request. `packages` runs typecheck and tests with `pnpm --filter "...[ref]"`, so only for the packages that changed and the ones that depend on them; it runs everything when `vectors/`, `fixtures/`, `scripts/` or the root config change. A docs-only change therefore still runs `repo` and `web`.
- A package can be split into its own repository later with `git filter-repo`.

## Golden vectors

The Python mcbuilder is the oracle: scripts call its real functions over a grid of inputs and write JSON into `vectors/`, and the TypeScript tests read that JSON. The vectors are generated, not copied from the old test assertions, so they can cover more inputs than the old tests did. `vectors/README.md` lists every file and the exporter that writes it.

- **Core:** `blocks.json` (block-state parsing and canonical strings), `rotation.json` (all four rotations: position transform and block-state transform for `facing`, `axis` and the rest), `structure-nbt.json` (compared as parsed structure before gzip, never as compressed bytes).
- **mcbuilder port:** `materials.json`, `shapes.json`, `geometry.json`, `build.json`, `registry.json` (validation against a small fixture registry, not the full asset cache), `report.json`, `config.json`, `importer.json`, `clean.json`, `diff.json`, `views.json`, and `examples.json` (a SHA-256 over every cell each example script builds).
- **Renderer:** `quads.json` (model-to-quads geometry and pixel hashes), `scenes.json` (occlusion, wall and fence connections, culling, ambient occlusion), `renders.json` (sizes and thumbnails of Python renders) and `guides.json` (guide text, layer image sizes and thumbnails).

The core and mcbuilder vectors are generated without network access or the asset cache. The renderer vectors need `mcbuild assets fetch --version 26.2` on a machine with network access, because they are computed from Mojang's assets. The JSON is committed, so CI never needs Python. The tests that read the renderer vectors, and the mesher test that compares against the CPU pipeline, also need the asset cache and skip without it. CI fetches the cache (and keeps it between runs), so it runs them; a machine without the cache skips 190 tests.

## mcbuilder port

The port starts from the merged `main` (mcbuilder 0.2.0, about 8,400 lines of Python and 453 test functions). Modules are ported in this order, each against its vectors or tests.

| Step | Python module (lines)                           | Note                                                                                                                       |
| ---- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1    | `voxels` (239), `geometry` (162)                | Dense numpy grid becomes typed arrays, with an adapter to `Volume`                                                         |
| 2    | `shapes` (467)                                  | box, walls, pillar, line, stairs, cylinder, sphere, cone, roof\_gable, roof\_hip; each is also a `Build` method, generated |
| 3    | `build` (312)                                   | The `Build` class, `rng()` namespaces, bounds errors                                                                       |
| 4    | `materials` (136)                               | `patches()`; SHA-256 based, so it stays portable                                                                           |
| 5    | `report` (92), `config` (110)                   | `report.json` and `mcbuild.toml` (needs a TOML parser)                                                                     |
| 6    | `importer` (296)                                | `.nbt` to builder script; the generated script becomes TypeScript                                                          |
| 7    | `diff` (362), `guide` (280)                     | numpy and Pillow move to typed arrays and a TypeScript rasterizer in `render`                                              |
| 8    | `render/faithful` (2,071), `render/views` (176) | Blockstate to model to quads, the grid logic and drawing all live in `render`                                              |
| 9    | `cli` (1,012)                                   | Commands: check, run, diff, import, init, assets (the spec's `view` is not built; see Status)                              |
| 10   | `assets` (291)                                  | Unzips the client jar and fetches the minecraft-data block registry                                                        |
| 11   | `examples/`                                     | Port every script; they are the end-to-end tests                                                                           |

**Status:** M5 is not complete. Done:

- **Steps 1 to 6** are ported in `packages/mcbuilder` and pass vectors exported from the Python oracle (`vectors/*.json`). Step 6 covers the importer's summary, constant naming, box merging and a TypeScript script writer; reading the `.nbt` itself is `core`'s codec. `mcbuild import` also reads `.schem`, `.litematic` and `.mcstructure`.
- **The `mcbuild` CLI** (in `packages/mcbuilder/src/node`): `init`, `check`, `run`, `import`, `diff` and `assets fetch`. `run` takes the DataVersion from the fetched `version.json` and falls back to a table of known versions.
- **Step 10 (assets):** tested against a fake network (`assets.test.ts`); CI runs `assets fetch` against the real servers (files already cached are skipped).
- **Step 11, the examples:** all 13 scripts are ported to `packages/mcbuilder/examples`. Eleven rebuild identically to the Python output (same cells, same bounds, same SHA-256 over every cell; `vectors/examples.json`). `homestead/watchtower` and `crystal_observatory` use the RNG: every position and every block the RNG does not place matches the Python output exactly, and only the RNG-picked blocks differ.
- **Step 7, `diff`:** the cell diff, the report text, run-id resolution and `.nbt` run loading match the Python oracle, and `mcbuild diff` works. Its comparison image is not written; the renderer it needs exists, the image is simply not ported.
- **Step 8, in `packages/render`,** checked against the Python renderer with vanilla assets fetched at run time: `views`; the blockstate-to-model-to-quads stage plus chest, banner, fluid and fallback-cube quads (77 blockstates, 916 quads: geometry within 1e-9, identical pixels, except the textured-cube pixels of `glass_pane` (two states), `lever` and `flower_pot`, where the original picks a texture in hash order and those four cases are skipped); and the grid logic (which blocks occlude, wall and fence connection inference, neighbour culling, per-vertex ambient occlusion: 5 scenes, 1,745 quads, all equal).
- **Previews:** `mcbuild run --preview` writes faithful PNGs (`--views`, `--count`, `--focus`) with the title, view label and compass, and warns about blocks drawn as magenta fallback cubes, as the original does. The rasterizer is TypeScript over typed arrays, `pngjs` writes the PNG, and text uses a small original bitmap font, so there is no native dependency. The test (`packages/mcbuilder/test/render.test.ts`) renders four builds in three views at 512 px without the overlay and compares the aspect ratio and a small thumbnail with `vectors/renders.json`: mean difference under 2.0/255, worst cell under 40/255. The CLI's own output (2048 px with the overlay) is not compared with Python anywhere.
- **Step 7, `guide`:** `mcbuild run --guide` writes `guide.md` and the layer images (with `--focus` it covers the focus box; the Python guide always covers the whole build). The test requires `guide.md` to equal the Python text for four builds (including the 13-layer underwater base) and the layer images to have the same sizes and thumbnails within 6/255.
- The renderer, quads, scene, preview and guide tests above need the asset cache and are skipped without it. They have not run on the development machine, which has none; CI has the cache and runs them (4 skipped there: the hash-order cases).
- The fast and trusted preview tiers are deliberately not ported, per the Decisions table ("Faithful tier first; fast and trusted only if the CLI needs them"): the CLI works without them and `--tier` says so. The fast tier's per-face texture resolver is ported (`packages/render/src/fast.ts`) because the guide uses it.

Not done:

- **`mcbuild view`: deferred to after 0.1.0 (decided 2026-11-07).** The spec's way to open a run in the editor. The command does not exist, and the web app has no entry point for a run directory. It is a small convenience and is not part of 0.1.0.
- **Parts catalog: out of 0.1.0 (decided 2026-11-07).** Named in the spec, but nothing defines it and the Python tool has no counterpart. It needs a definition before it can be scoped or built.
- **Error provenance.** Python's registry errors say `(at file:line)` of the script line that placed the block, and its script errors carry the script path and line. The port prints neither.
- **`diff` comparison image** (`diff-<a>-<b>.png`).
- **`Build.validate` and `Build.render`** in the library API. Validation is reachable through `Registry`, rendering through `renderView` in `@voxwright/render`.
- **User documentation** for the CLI and the builder DSL (the port renamed it: camelCase, `scope()`, option objects), and the example `mcbuild.toml` files. The waystones examples need `allowlist = ["lostqol:waystone"]`; `examples/waystones/common.ts` mentions a `mcbuild.toml` that does not exist in the port.
- **CLI test parity.** `packages/mcbuilder/test/cli.test.ts` has 13 tests; the Python `test_cli.py` has 37. Some are missing because the feature is missing (provenance), others are plain gaps (`init` variants, the allowlist warning).
- **Proxy.** `assets fetch` uses Node's `fetch`, which ignores `HTTPS_PROXY` unless `NODE_USE_ENV_PROXY=1` is set; the Python tool detected a proxy itself.
- **Archive `lzif/mcbuilder` with a pointer** (the last step of M5). Not done, and Luki's call.

## Port gotchas

- **RNG:** `Build(seed=...)` uses Python's Mersenne Twister with SHA-512 string seeding. The port uses a new PRNG, so seeded builds differ from Python; the vectors only cover paths that do not use the RNG.
- **Scripts:** builder scripts are Python today. After the port they are TypeScript, so every script in `examples/` must be ported.
- **numpy and Pillow:** numpy became typed arrays with small helpers. Pillow became a pure TypeScript rasterizer (`packages/render/src/rasterize.ts`, `image.ts`, `draw.ts`, `font.ts`) with `pngjs` for PNG output; no `@napi-rs/canvas` and no `PreviewSurface` interface were built. This was the spec's own fallback for a native canvas; it is listed under "Differences from the v1 spec" because the Decisions table does not record it.
- **Determinism:** `cli.py` re-executes itself with `PYTHONHASHSEED=0`. Node needs no such step, but any iteration order that affects output must be explicit.
- **Assets:** fetching the client jar needs zip extraction (a small dependency such as fflate) and the PrismarineJS minecraft-data block registry.
- **Test baseline at the PR #5 merge:** 506 pass, 26 are skipped because they need the real asset cache, and 1 (`test_inferred_fence_renders_connected_not_fallback`) fails without the cache because it lacks the `needs_real_assets` marker.

## M1 status

**Status:** the viewer runs on WebGL2. `packages/render/src/mesh` is the DOM-free part: a section mesher (one 16x16x16 section plus a one-cell border from its neighbours becomes positions, atlas UVs, a per-vertex colour that carries tint, face shade and ambient occlusion, and indices, in an opaque, a cutout and a translucent bucket), a texture atlas builder (animated textures are their first frame), and a scheduler that feeds a pool of workers and keeps a slow worker from overwriting a newer mesh. It reuses the quad pipeline of the CPU renderer (`models.ts`, `blocks.ts` and `scene.ts` in `packages/render/src`; `core` has no quad code), so models, multipart, chests, banners, fluids, wall and fence connections, neighbour culling and ambient occlusion are the same code; unknown blocks are the magenta fallback cube. `@voxwright/render/webgl` is the browser entry point (three.js, the `Renderer` interface, orbit and fly cameras, clip-plane slicing with re-meshed cut layers, highlight boxes); `.dependency-cruiser.cjs` keeps three.js out of everything else and forbids importing `src/webgl` from the rest of `render`; the rest of `render` and `core` stay free of the DOM because their `tsconfig` has no DOM library. So the `mcbuild` CLI never reaches three.js. `apps/web` uses the WebGL renderer, with an orbit and fly toggle and the layer slicer; it imports the concrete `WebglRenderer` and calls members that are not in the `Renderer` interface (`rayFromClient`, `setPack`, `setOrbit`, `getPose`, `whenMeshed`, `whenIdle`, `stats`), so the interface is not what the app depends on (listed under "Differences from the v1 spec"). It falls back to the CPU renderer when WebGL2 is missing; that is a separate worker path, not a second `Renderer`. Convert and the loss report are unchanged. `apps/web/test/e2e.ts` drives both paths in Chromium on the Rafeals_house fixture.

## M3 status

**Status:** the editor works in `apps/web`, on the WebGL path. **Loading an edited file in Litematica itself was checked by Luki on 2026-11-11** (Litematica is not available on the development machine, so this is his own check, not a test here); he then closed M3 (#16). The spec's other half, that rotate and mirror reproduce the golden rotation vectors, is covered by the core tests that existed before this milestone.

**What is there.** The editor core (`Editor`, `Stroke`, `History`, `DirtyTracker`, the tools, `raycast`) was committed earlier; M3 wires it into the page. `apps/web/src/lib/editor-session.svelte.ts` holds the open volume's `Editor`, the chosen tool, block and selection, and turns mouse and keyboard into core commands; after every change `editor.dirty.take()` goes to `renderer.markDirty`. The panels are Svelte components in `apps/web/src/lib/components` (toolbar, block palette, block-state panel, selection panel); the pure parts (tool list and shortcuts, palette search, ray helpers) are in `lib/editing.ts`.

- **Tools:** place, replace (turns the clicked block into the chosen one), erase, eyedropper, line, rectangle (filled or hollow), box select, fill, replace A with B inside the selection, copy, paste, move (by typed offsets), rotate 90 degrees either way, mirror east-west or north-south. Erase writes air, so the build keeps its size.
- **Input scheme:** the page starts in View, where the mouse only looks around as before. With a tool chosen, a plain left click or drag uses the tool, Alt+drag turns the view, Shift+drag or the right button moves it sideways, the wheel zooms. Tools work in the Orbit camera only; Fly is unchanged. A drag with Place, Replace or Erase is one undo step and stays on the surface it began on; line and rectangle show a ghost box while dragging and are one command on release. Keys: V view, P place, B replace, X erase, I eyedropper, L line, R rectangle, M select, F fill, `[` and `]` rotate, Ctrl+C and Ctrl+V, Esc cancels or deselects, Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y for history. None of the single keys is a fly key. Keys are ignored while typing in a text field (the palette search, the property and coordinate fields). Shortcuts are in the tooltips and the interaction is explained in the page's help text.
- **Picking:** core's `raycast` along the camera ray. The renderer gained `rayFromClient(x, y)` (a pure `pickRay` in `controls.ts`, checked against three.js's own camera) and, for tests, `clientFromWorld`. Core's `raycast` gained an optional `accept(x, y, z)` callback; the page uses it so that cells outside the layer slice are passed through, and it refuses to place a block outside the slice. The ray is first clipped to the volume's bounds, so a miss costs nothing.
- **Palette:** block ids from the pack's blockstates (`blockstates/<name>.json` in `pack.json`) and the open volume's own block states, searchable by words; without a pack only the volume's blocks are listed. Any block can be typed, with properties.
- **Block-state panel:** `blockProperties` for the block last pointed at (it stays when the pointer moves to the panel). Booleans are a drop-down; other values are an input with the suggestions as a datalist, so any value can be typed; a new property can be added. In the mobile layout (MB6) the same panel draws switches, chips and steppers, a Rotate block button and the text fields behind "Other…", for the block last tapped.
- **Export:** converting now encodes the page's current volume, through core's codecs and the loss report, on the main thread (the worker's copy of the file is only used by the software renderer). The file opened is never written; the download is a new file, named `<name>-edited.<ext>` once there are edits.
- **Unsaved edits:** `beforeunload` asks while there are edits that were neither exported nor undone, and opening another file asks first. This is slightly narrower than "history is not empty": exporting counts as saving.

## Differences from the v1 spec (decided 2026-11-07)

The code differs from the v1 spec in the ways below. Luki decided all fourteen on 2026-11-07; each entry ends with its verdict. No code changes with these decisions.

- **Volume shape:** the spec has an interface with `origin`, `size`, `palette: BlockState[]` (index 0 is air), `sections` as `Uint16Array` (absent means all air), `dataVersion` and `meta`. The code has a `Volume` class: the palette is a list of block strings, sections hold `Int32` indices where -1 means "never set" (kept apart from explicit air), `origin` and `size` are not stored (they come from the set cells, `placedBounds()`), and `dataVersion` and the file's name, author and description travel in each codec's `meta` result, not on the `Volume`. **Verdict: keep the `Volume` class.**
- **Report shape:** the spec's codecs return a report of the form `{ lost: Loss[] }`; the code returns `warnings: string[]`, one line per kind of loss. **Verdict: keep `warnings: string[]`.**
- **Quad generation:** the spec puts it in `core`; the code has it in `packages/render`. **Verdict: keep it in `packages/render`, not `core`.**
- **Renderer interface:** the spec has the web app talk only to `core` and the `Renderer` interface; the app uses the concrete `WebglRenderer` and members outside the interface, and the CPU fallback is a separate worker path. **Verdict: keep the app using the concrete `WebglRenderer`.**
- **CLI previews:** the spec proposes Canvas 2D through `@napi-rs/canvas` behind a `PreviewSurface` interface, with a pure TypeScript rasterizer as the fallback; the code has only the rasterizer (the spec's own fallback), and no interface. **Verdict: keep the pure-TypeScript rasterizer only.**
- **Browser checks:** the spec asks for Playwright screenshots of three fixtures with a loose tolerance, in CI only; the code has a Puppeteer run (`puppeteer-core`) on one fixture, `Rafeals_house`, that checks pictures by hash and colour counts and keeps no reference images, and it also runs locally. **Verdict: keep the Puppeteer run on Rafeals_house.**
- **Styling:** the spec lists Tailwind; the app has hand-written `<style>` blocks and no Tailwind. **Verdict: keep hand-written CSS, no Tailwind.**
- **Hosting:** the spec lists Cloudflare Pages; the code has no Cloudflare configuration and no deploy workflow, only a static build (`adapter-static`) for any file host. **Verdict: keep the static build for any host, no Cloudflare configuration.** (2026-11-11: since 2026-11-09 `.github/workflows/pages.yml` publishes that static build to GitHub Pages; there is still no Cloudflare configuration.)
- **Asset fetch:** the spec names one `pnpm assets:fetch`; the code has two commands, `node packages/mcbuilder/bin/mcbuild.ts assets fetch --version 26.2` and `pnpm --filter @voxwright/web assets`, and no `assets:fetch` script. **Verdict: keep the two commands.**
- **Bedrock names and states:** the spec asks for a mapping from an open-source table with its licence checked; the code translates block states by hand-written rules (`packages/core/src/codecs/bedrock.ts`), has two renames, passes unknown names through unchanged, and the table item under Open items is unresolved. **Verdict: keep the hand-written rules.** Which mapping table to adopt, if any, is a separate decision and stays open (see Open items).
- **`core` package:** the spec describes a reusable library; `@voxwright/core` is `private` at version `0.0.0`, and `exports` points at `.ts` source with no build output, so it is reusable inside this monorepo only. **Verdict: keep it private at 0.0.0 for 0.1.0.**
- **Guide and `--focus`:** the Python guide covers the whole build; the port's `mcbuild run --guide` crops it to the `--focus` box. **Verdict: keep cropping the guide to the focus box.**
- **Fast-tier textures:** for `glass_pane`, `lever` and `flower_pot` the Python code picks "any usable texture" in hash order; the port takes the first in model order, which can change the guide's top texture for those blocks. The test for the four affected cases is skipped. **Verdict: keep first-in-model-order (deterministic).**
- **Parts catalog and `mcbuild view`:** the spec names both for M5; neither is built (see the M5 status). **Verdict: defer both; neither is in 0.1.0.** The parts catalog was never defined (the spec names it, nothing else does) and needs a definition before it can be scoped or built. `mcbuild view` is deferred to after 0.1.0. See the M5 status.
